<objective>
Cross-check the documented parser design against the current implementation for the
January 2026 / December 2025 rollover bug, then define the implementation plan for
fixing both the code path and any already-imported bad data.

Output: diagnosis plus an actionable fix plan. No product code changes in this task.
</objective>

## Diagnosis

### What the docs say

- Phase 2 research explicitly calls out cross-year inference as a primary pitfall and
  says transaction dates must be assigned to the year that places them within the
  statement period.
- The Phase 2 context locks in the same approach: use statement-period context for
  Dec/Jan rollover.
- The parser plan and verification docs both claim cross-year inference is handled.

Evidence:
- `.planning/phases/02-pdf-import-pipeline/02-RESEARCH.md` says to extract the
  statement period first, then assign the year that makes the transaction fall within
  that period.
- `.planning/phases/02-pdf-import-pipeline/02-CONTEXT.md` decision `D-19` says the
  parser should extract statement period context first and then infer the correct year.

### What the implementation actually does

- The explicit statement-period path is correct enough for cross-year handling:
  `inferTransactionDate()` tries start year and end year and picks the one within the
  period.
- The real-PDF fallback path is where the bug lives. When the summary pages are
  image-only and the parser falls back to inferring the period from transaction rows,
  it parses every transaction date using the hint year only.
- For a Jan 2026 statement that includes Dec 2025 rows, this turns `28 DEC` into
  `2026-12-28` during fallback inference, so the inferred period becomes a 2026-only
  range. After that, downstream transaction inference is operating on the wrong period,
  and December rows remain in 2026.

Evidence:
- `src/lib/parser/parse-statement.ts` fallback block comments “try hint year - 1 for
  cross-year”, but the code never actually does that.
- The current fallback test covers Jan-Feb 2026 only and does not exercise a Dec/Jan
  rollover case, so this regression slipped through.

### Root cause

Doc / implementation mismatch in the fallback parser path:

1. Docs assume we always have a trustworthy statement period or an equivalent fallback.
2. Real Citibank PDFs often do not expose the statement-period header in extractable
   text, so the app uses `period_fallback`.
3. That fallback path does not implement the documented cross-year logic.
4. Existing tests validate the explicit-period path but not cross-year fallback.

## Fix Plan

### 1. Repair fallback statement-period inference

Update `src/lib/parser/parse-statement.ts` so fallback period inference can derive a
cross-year range from transaction rows plus a year hint.

Recommended implementation:

1. Extract the hint year exactly as today from `Payment Due Date`.
2. For each matched transaction date `dd MMM`, parse two candidates:
   - candidate A: `hintYear`
   - candidate B: `hintYear - 1`
3. Select the candidate set that forms the tightest plausible statement window instead
   of a nearly year-long span.
4. Derive `periodStart` and `periodEnd` from the chosen normalized dates.

Pragmatic rule for v1:

- If the parsed months span a Dec/Jan rollover, assign months greater than the hint
  month to `hintYear - 1`, and months less than or equal to the hint month to
  `hintYear`.
- Example: hint year 2026, transactions in Dec and Jan:
  - `DEC` => 2025
  - `JAN` => 2026

Safer variant:

- Build normalized dates using month comparison against the maximum month range actually
  present in the statement and reject any inferred range longer than ~62 days.
- If the inferred period exceeds the safe window, return a parse error instead of
  silently creating a corrupt range.

### 2. Keep transaction-level inference aligned with fallback period

After fixing the fallback-derived `periodStart` / `periodEnd`, keep using
`inferTransactionDate()` to assign each transaction’s final ISO date. The main bug is
the fallback period; once that is corrected, the existing transaction-level inference
should behave consistently.

Optional hardening:

- Add a validation pass after transactions are built:
  - if an inferred transaction date is implausibly far outside the inferred statement
    period, fail parsing rather than importing suspect data.

### 3. Add regression coverage

Add parser tests for the exact failure shape:

1. Fallback path with `Payment Due Date: January ... 2026` and transaction rows
   containing both `DEC` and `JAN`.
2. Assert `statementPeriodStart` resolves to a 2025-12 date and `statementPeriodEnd`
   resolves to a 2026-01 date.
3. Assert a December transaction becomes `2025-12-xx`, not `2026-12-xx`.
4. Assert a January transaction becomes `2026-01-xx`.

Keep the existing Jan-Feb fallback test as a non-cross-year control.

### 4. Bring docs back in sync

Update Phase 2 docs so they describe the actual supported fallback behavior, not only
the idealized explicit-period path.

Minimum doc updates:

1. `.planning/phases/02-pdf-import-pipeline/02-RESEARCH.md`
   - add a note that real Citibank PDFs often require fallback period inference
   - document the Dec/Jan rollover rule in the fallback path
2. `.planning/phases/02-pdf-import-pipeline/02-01-PLAN.md`
   - add a specific acceptance criterion for fallback cross-year statements
3. `.planning/phases/02-pdf-import-pipeline/02-VERIFICATION.md`
   - verify the new regression test exists and passes

## Current Data Remediation Plan

### Goal

Correct already-imported rows that landed in December 2026 but should be December 2025,
without damaging valid 2026 data.

### Recommended remediation approach

Use a targeted SQL remediation migration or admin script, not ad-hoc manual updates.

#### Step 1: Identify affected imports

Find imports likely produced by the broken fallback path:

- imports where `statement_period_start` / `statement_period_end` show an implausible
  nearly year-long range for what should be a monthly statement, or
- imports whose filename / import date corresponds to the reported January 2026
  statement, or
- imports containing December 2026 transactions together with January 2026 transactions
  in the same import.

#### Step 2: Preview candidate rows before updating

Create a SELECT-only audit query that lists:

- `imports.id`
- `imports.file_name`
- `transactions.id`
- `transactions.transaction_date`
- `transactions.description`
- `transactions.amount_cents`

Candidate filter for this bug shape:

- transactions in `2026-12-*`
- belonging to an import that also contains `2026-01-*`
- and where the import was expected to represent a Jan 2026 statement / monthly window

#### Step 3: Update only the wrong December rows

For confirmed affected imports:

1. Update `transactions.transaction_date` from `2026-12-xx` to `2025-12-xx`.
2. Recompute `transaction_hash` for those rows because the hash includes the date.
3. If the `imports` statement period fields are wrong, update
   `imports.statement_period_start` / `statement_period_end` to the corrected Dec 2025
   to Jan 2026 range.

Important:

- Rehashing is mandatory. Leaving the old hash in place will break duplicate detection.
- Run remediation inside a transaction.
- Save an audit snapshot of affected rows before mutation.

#### Step 4: Revalidate affected screens

After remediation, verify:

- import history period display is correct
- dashboard month aggregations no longer show phantom Dec 2026 spending
- duplicate detection still behaves as expected for any re-upload of the same statement

### Safer operational alternative

If affected data volume is small and tied to one or two imports, a simpler and lower-risk
option is:

1. identify the bad import IDs
2. delete transactions for those import IDs
3. delete the corresponding import records
4. re-import the PDFs after the parser fix ships

This is often safer than mass row surgery because it lets the corrected parser recreate
canonical hashes and statement-period metadata.

Preferred choice:

- If only a few imports are affected, delete-and-reimport is the cleanest recovery path.
- If many imports are affected or original PDFs are unavailable, use the targeted update
  script with rehashing.

## Risks

- A naive data fix can corrupt legitimate December 2026 transactions if the filter is
  too broad.
- Updating dates without updating hashes creates silent duplicate-detection bugs.
- Fixing fallback logic without adding a Dec/Jan regression test risks reintroducing the
  issue later.

## Validation Steps

1. Add a failing regression test for fallback Dec 2025 / Jan 2026 before changing code.
2. Implement fallback fix until the regression passes.
3. Run the full parser test file.
4. Dry-run the remediation query and manually inspect candidate rows.
5. Apply remediation in a transaction on a backup or preview environment first.
6. Re-check dashboard totals and import history for affected statements.

## Recommended Order

1. Add regression test covering fallback Dec/Jan rollover.
2. Fix fallback period inference in `parse-statement.ts`.
3. Re-run parser tests.
4. Prepare a SELECT-only remediation query and review candidate rows.
5. Choose remediation mode:
   - delete and re-import, if the bad imports are limited and PDFs are available
   - targeted update + rehash, if re-import is not practical
6. Update docs and verification notes so the implemented behavior matches the written
   design.
