    **Create `src/app/actions/user-management.ts`** (Server Actions):

    ```typescript
    'use server';
    ```

    This file uses the Supabase **service role key** (not the anon key) because user creation via `supabase.auth.admin.createUser()` requires admin API access. Create a separate admin client:

    ```typescript
    import { createClient as createAdminClient } from '@supabase/supabase-js';
    import { createClient } from '@/lib/supabase/server';
    import { Database } from '@/lib/types/database';

    function createServiceRoleClient() {
      return createAdminClient<Database>(
        process.env.NEXT_PUBLIC_SUPABASE_URL!,
        process.env.SUPABASE_SERVICE_ROLE_KEY!
      );
    }
    ```

    **Action: `createUser`**
    - Input: `{ email: string; fullName: string; role: 'admin' | 'viewer' }` -- validate with Zod schema
    - Zod schema: `email` is `z.string().email()`, `fullName` is `z.string().min(1).max(100)`, `role` is `z.enum(['admin', 'viewer'])`
    - First verify caller is admin: use `createClient()` (server client with user session), fetch caller's profile, check role is 'admin'. Return `{ error: 'Unauthorized' }` if not admin.
    - Create auth user: `serviceRoleClient.auth.admin.createUser({ email, password: crypto.randomUUID().slice(0, 12), email_confirm: true })` -- temporary password, user resets via email
    - After auth user created, insert profile: `serviceRoleClient.from('profiles').insert({ id: authUser.id, email, full_name: fullName, role, household_id: '00000000-0000-0000-0000-000000000000' })`
    - Send password reset email so user can set their own password: `serviceRoleClient.auth.admin.generateLink({ type: 'magiclink', email })` or use `resetPasswordForEmail`
    - Return `{ success: true }` or `{ error: string }`
    - On success, call `revalidatePath('/settings')` to refresh the page data

    **Action: `removeUser`**
    - Input: `{ userId: string }` -- validate with Zod
    - Verify caller is admin (same pattern as createUser)
    - Check if target user is the last admin: query `profiles` for count of admins. If removing the only admin, return `{ error: 'You are the only admin. Add another admin before removing yourself.' }` (per D-16, Copywriting Contract "Last admin warning")
    - Delete auth user: `serviceRoleClient.auth.admin.deleteUser(userId)` -- this cascades to profiles via FK ON DELETE CASCADE
    - Return `{ success: true }` or `{ error: string }`
    - Call `revalidatePath('/settings')`

    **Action: `updateUserRole`**
    - Input: `{ userId: string; newRole: 'admin' | 'viewer' }` -- validate with Zod
    - Verify caller is admin
    - If demoting an admin to viewer: check if they're the last admin (same protection as removeUser, per D-16)
    - Update: `serverClient.from('profiles').update({ role: newRole }).eq('id', userId)`
    - Return `{ success: true }` or `{ error: string }`
    - Call `revalidatePath('/settings')`

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client to Server Actions | User management operations cross from client to server action boundary |
| Server Action to Supabase Admin API | Service role key grants admin-level Supabase access |
| Settings page access | Non-admin users must not access user management |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation |
|-----------|----------|-----------|----------|-------------|------------|
| T-03-01 | Elevation of Privilege | Server actions | High | Mitigate | Every server action (createUser, removeUser, updateUserRole) verifies the caller is an admin by querying their profile. Non-admins get `{ error: 'Unauthorized' }`. Server-side check, not just UI hiding. |
| T-03-02 | Tampering | Service role client | High | Mitigate | Service role key (`SUPABASE_SERVICE_ROLE_KEY`) only used in server actions, never exposed to client. Key stored in `.env.local` (gitignored). Used only for `auth.admin.*` operations that require elevated access. |
| T-03-03 | Elevation of Privilege | Last admin removal | Medium | Mitigate | Server action checks admin count before removal or demotion. Prevents lock-out scenario where no admin exists (D-16). |
| T-03-04 | Spoofing | Settings page access | Medium | Mitigate | Server component checks caller's profile role before rendering. Non-admins redirected to /dashboard. Server-side redirect, not client-side hiding. |
| T-03-05 | Tampering | Input validation | Medium | Mitigate | All server action inputs validated with Zod schemas (email format, name length, role enum). Invalid input rejected before any database operations. |
| T-03-06 | Information Disclosure | User list | Low | Accept | All household members can see other members' names and emails (via RLS SELECT policy). This is by design for a household app with 2-3 users. No sensitive data beyond name/email/role exposed. |
